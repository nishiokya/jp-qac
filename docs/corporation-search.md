# 法人検索の構成と段階的な改善

確認日: 2026-11-05。対象: nishiokya/jp-qac。

## 今回の構成

ブラウザ SDK → Fastify の既存 `/v1/corporations` → サーバー側 NTA provider → 国税庁 Web-API v4。
郵便番号は既存の SQLite を引き続き使用する。公開 API のレスポンス形式と SDK の `fill` は変更しない。

既存 provider は `type=12` の応答を JSON として扱い、`kind=01` で国の機関だけに限定していた。XML の検証・解析を行い、種別指定を外す。入力された半角英数・カナは国税庁への送信時に全角へ変換する。`change=0`、`close=0` により、名称検索は現在の情報・閉鎖を除く法人を対象にする。法人番号による照会は `history=0` で最新情報を取得し、閉鎖状態も返す。

XML の文字列値を保持し、公開するフィールドだけを取り出す。DTD・カスタム実体、壊れた XML、不正な構造は汎用 502 エラーにする。接続失敗・タイムアウトは汎用 503。上流 URL、応答本文、元の例外をログやクライアントへ渡さず、リダイレクトを追従しない。

## 現状のデプロイと UX

`render.yaml` は Node の無料 Web サービスで、郵便番号 DB はビルド時に生成する。既存のデプロイ手順ではファイルを永続保存しない運用としている。本番の環境変数・デプロイ実態は今回変更・検証していない。ID は Render のサーバー環境変数 `NTA_APPLICATION_ID` で管理する。

SDK は２文字から250msの待機後に候補を検索し、候補選択で法人番号・郵便番号・所在地を補完できる。現在は最初の応答ページから `limit` 件を返すため、全件取得や関連度順のランキングではない。国税庁は名称検索の2,000件超を分割する。今回ページ巡回は追加しない。

既存 SDK には、IME 入力中の検索、古い応答の競合、法人選択によって郵便番号検索が発火し共有住所欄を上書きする可能性が残る。次段階ではこれらの回帰テストを先に追加する。法人住所と郵便番号の町域は同じ粒度ではないため、法人選択後は法人住所を優先し、ユーザーが郵便番号を編集したときだけ郵便番号補完を行う設計とする。

## 公開ダウンロードからのインデックス（次段階・未実装）

全件は Web-API では取得できない。初期投入は公式の Unicode CSV ダウンロードを利用する。確認時の全国 ZIP は256MBで、展開後のデータと索引はさらに容量が必要になる。現行 Web ビルドへの追加はせず、独立した取込処理で生成する。

1. まず一都道府県でストリーミング取込を検証し、メモリ・所要時間・索引サイズを測る。法人番号を主キーとし、名称・カナの正規化キーと所在地コードを保持する。
2. 日本語の前方一致を索引で処理し、部分一致は候補絞り込みと計測後に導入する。SQLite FTS の一般的な単語分割だけで日本語サジェストが成立すると仮定しない。
3. 全国データは Web プロセス外で生成・検証し、件数・取得日・チェックサム付きのスナップショットを原子的に差し替える。旧版を残してロールバックできるようにする。常時更新するなら永続ストレージを確保する。
4. 差分は日付の連続性、閉鎖・訂正・検索対象除外・重複適用を扱い、欠落時は全件から再構築する。更新失敗時は前回成功日を表示する。
5. サジェストはローカル索引、選択時の詳細照会はサーバー側 Web-API とする案を検証する。上流負荷を抑える共有キャッシュ・同一要求の集約・アクセス制御も合わせて設計する。
